# AI パーツ分離：候補比較と評価計画

初回調査日: 2026-10-09（日本時間）。以下は初回の資料調査。追加承認後のモデル導入・自前推論・試作の結果は [AI_PROTOTYPE_RESULTS.md](AI_PROTOTYPE_RESULTS.md) を参照。

## 結論と推奨案
背景除去だけでは髪・顔・目・衣装は分離できない。点や枠を指定して部分を識別するモデルも、指定なしでパーツ名を判断するとは限らない。
まず「利用者がパーツ名を選び、点・枠で対象を示す → AI が見えている領域を切り抜く」方式を試す案を推奨する。
背景除去の補助候補は rembg + BiRefNet-general-lite、部分を切り抜く候補は SAM 2.1 tiny/small。
これは評価候補であり採用決定ではない。完全自動から補助操作へ移す場合は重要な仕様変更としてオーナーの承認を得る。
隠れた部分の描き足し、前髪・後髪や左右の目の細分化、Live2D の動作付けは別課題として扱う。

## 候補の比較

| 候補 | 資料で確認できた機能 | 不足・評価が必要な点 | 実行環境・条件 | 費用と画像の扱い |
|---|---|---|---|---|
| rembg + BiRefNet-general-lite | 背景除去。rembg は CPU/GPU、Python ライブラリ・HTTP サーバー等に対応 | パーツごとの名前・領域の認識はしない。イラストの細い髪・半透明部分は未検証 | rembg は Python 3.11 以上 3.14 未満。CPU は ONNX Runtime。軽量モデルも実測が必要 | 自前実行なら第三者 AI API への送信は不要。計算機・運用費は必要。rembg と BiRefNet のコードは MIT。採用する重みと依存物の条件は個別確認 |
| SAM 2.1 tiny/small | 静止画に点等の指示を与え、対象のマスクを推定。複数サイズの重みあり | 髪等の名前を自動で割り当てる処理は別途必要。輪郭マスクから透明 PNG を作る後処理が必要。隠れた部分を生成しない | 公式は Python >=3.10、torch >=2.5.1、torchvision >=0.20.1。GPU の導入例。CPU 実用速度・当環境の GPU は未確認 | 公式 README は重み・デモ・学習コードが Apache 2.0 と明記。自前推論は画像を第三者 AI API に送らずに運用可能。GPU 等の運用費は別 |
| 外部ホスト型 API（例: Replicate） | BiRefNet 公式 README に外部エンドポイントへのリンクあり | ホスト側の実装・モデル版・料金・保管・学習利用・商用条件は未確認 | アカウント、秘密情報、許可した送信先、課金管理が必要 | 今回、公式料金と保存期間ページはプロキシの 403 で取得できず。採用候補として保留。画像を第三者に渡すため別途承認 |
| 完全自動の専用パーツモデル | 今回、条件を満たす方式の採用判断はできていない | イラスト向け分類、左右・前後のラベル、学習データの権利、隠れ領域補完が必要 | 専用学習を行う場合はデータと GPU、評価作業が必要 | 費用・データ扱い未確定。初期方式として約束しない |

rembg は複数のモデルを選べる道具であり、すべてのモデルの利用条件が同じではない。BiRefNet の README は BRIA RMBG-2.0 の重みの非商用制限に言及しており、MIT のツールだから任意の重みを商用利用できると解釈しない。
BiRefNet の公開速度・GPU メモリ値は特定機器や精度設定の参考値。軽量モデルや本アプリの処理時間の保証には使わない。

## 費用の見積もり方
実測も料金確認も未完了なので、確定費用は出せない。
- 自前常時サーバー: 月額 = 時間単価 × 稼働時間 + ストレージ・通信・運用費。
- 従量処理: 画像一枚 = 時間単価 × 請求対象秒数 ÷ 3600。初回起動、再試行、失敗時課金、最低料金を加味する。
- 例として、仮の単価 1 米ドル/時・請求対象 10 秒なら計算費は約 0.0028 米ドル/枚、1000 枚で約 2.78 米ドル。これは提供元の見積もりではなく計算例。
- 同じ仮単価で 30 日常時稼働なら 720 米ドル/月。低利用では停止・起動設計が重要。
- 実際の単価・税・為替・無料枠・予算上限は契約前に確認する。現段階で費用を発生させない。

## 評価の進め方（実行前に承認）
1. 利用権のある静止画 12 枚を準備する。正面・横向き・全身・髪の重なり・細い線・半透明や複雑背景を含む。一般公開画像を無断で評価素材にしない。
2. 各画像の髪・顔・目・衣装について、見えている領域の正解マスクを作る。存在しないパーツも記録する。画像は GitHub に入れず、保管場所・期間・削除方法を承認する。
3. 権利表示とハッシュを記録したモデル版を固定する。CPU の背景除去から開始し、SAM は利用可能な機器を確認して実行可否を決める。
4. 冷起動と起動後を分け、同条件で少なくとも 3 回計測する。入力サイズ・OS・CPU/GPU・メモリ・モデル版・指示回数を記録する。
5. マスク精度、輪郭の見た目、必要な修正回数と時間、処理時間、最大メモリ、失敗率を記録。出力 PNG の透明度・寸法・位置を検証する。
6. 小さな画像に合わせた仮目標: 1024 px 入力で起動後 30 秒以内、対象領域の IoU（重なり率）中央値 0.85 以上、致命的な取り違えがない画像 10/12 以上。これは合意前の評価基準案で、達成を約束しない。髪の細部は目視も必要。
7. 12 枚は初期判断用に限定する。合格後に未知の画像と実機で拡張評価し、採用・改善・中止をオーナーへ提案する。

評価結果表の列: sample_id / 権利確認 / パーツ / モデルとハッシュ / 機器 / 入力寸法 / 点・枠の回数 / IoU / 輪郭所見 / 冷起動秒 / 起動後秒 / ピークメモリ / 修正分 / エラー / 判定。

## 接続設計案（未実装）
- 既存の画面と src/separator.js の入口を維持し、API 通信の処理を分ける。デモは明示して残す。
- サーバー側は Python + FastAPI を候補とする。認証情報・モデル読込はサーバー側。モデル版、画像寸法、パーツ ID を検証する。
- 入力: 画像、選択パーツ、任意の正規化した点・枠。出力: 元画像と同じ幅・高さの透明 PNG、パーツ ID、モデル版、処理の状態と警告。
- マスクは元画像の座標へ戻し、RGB は元画像を使い alpha にマスクを適用する。位置がずれないことをテストする。隠れた画素は補完しない。
- 存在しない対象は成功した空画像として扱わず、「見つからない」と表示。勝手に別のパーツを代用しない。
- 非同期処理にする場合は依頼 ID、進捗確認、中止、時間制限、同時実行数制限を用意する。ブラウザの通信中止だけではサーバーの計算停止を保証できない。
- スマホの高負荷処理を避けるためサーバー実行を基本候補にする。ただし自前サーバーへの画像送信・保管についても説明と承認を得る。
- 生画像をログに残さず、学習へ流用しない設計を提案。保持期間や終了時の破棄は承認後に実装する。

## 必要な承認と次の最小作業
推奨する次の範囲は「自前環境での技術試作と、明示的に利用を許可された画像による評価」。
- 点・枠による補助操作を初期方式として試してよいか。
- 機器の確認、依存関係・モデルのダウンロード、試作サーバー実装、無課金のローカル推論を行ってよいか。
- サンプル画像の入手・保管条件と評価基準。外部画像送信は含めない。
GPU が必要でも有料機器を勝手に借りない。使える機器がなければ CPU の可否を調べ、速度不足を報告する。
外部 API を採用する場合は、料金・保持・学習利用の条件を追加確認して別の承認を得る。
main マージ、Web 公開、Live2D モデル化は引き続き承認対象。
