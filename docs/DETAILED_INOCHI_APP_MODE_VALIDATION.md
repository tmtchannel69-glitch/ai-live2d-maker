## 実物の記録

入力は以前の提供JPEG、191,295bytes、SHA`04a40e3ebcea23b4f6253eeaca12699df61fa70998a161ca6ce2733477304a4e`。既存私用ZIPのinputから取り出して別の私用フォルダへ保存し、元ZIPは変更していない。既存のローカル依存/固定重みを使い、モデルを自動取得しなかった。

元CLIの処理は81.054秒。アプリは2回の実験で、中止各1回＋完了各1回。完了時の計測は約86.61秒と131.20秒（後者は並行テスト中で、速度保証ではない）。2回ともheadモデルSHA`a759efab3bb02d8e8f1b9eb74398d2741e0863319dc88cf0c4915fd854f0ffde`で旧head CLIと全バイト一致。ZIP全体は出力時刻/provenanceで異なり、モデルとは別の比較とする。

最終の検証ZIPは6,270,701bytes、119項目、展開後17,105,751bytes、CRC成功。共通graph38項目の参照PNG/マスクを含み、原JPEG/source-image/一枚の再構成/未参照ファイルは含まない。各entryのSHAが元JPEGと異なることも照合した。生成したパーツに元の観測画素を保持することと、元ファイルを入れないことを区別する。作業保存ZIPは従来どおり元画像を含む別用途の形式。

独立CPUは頭10状態で検査した首6,004画素の透明0、胴体の検査領域の差0、中立の旧モデルとの差0。瞬き10状態の診断も同梱。観測パーツのRGBA再構成は一致し、隠れた首/胴体の領域は推定と記録する。これらは公式SDKや自然さの代替判定ではない。

従来5パーツも実画像をローカルAPIへ送り、13項目ZIP/CRC/元ファイル除外を確認。モデルSHA`dfc65b5dbb9c7e99852d6e7b710bb9b72f600d72cf871a0fe020660d04d327e9`が以前の安定版と一致。最初の比較では詳細CLI内の品質版5パーツを対象にしてしまい一致しなかったので、正しい従来5パーツの記録と照合し直した。生成器を変更して検査を通したものではなく、旧generate関数のASTも44b74d9と一致する。壊れた入力の実API応答400と、その後のロック解放も確認。
