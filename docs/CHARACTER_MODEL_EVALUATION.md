# 提供キャラクター画像からの実モデル評価

2026-10-20、`feature/character-model-evaluation`。オーナーが再添付した画像を、このクラウド内だけで分離・モデル化・描画した。画像を外部AIサービスへ送らず、元画像・マスク・モデル・比較画像はGitへ保存していない。

**結論：実画像からMOC3を生成して描画する経路は動いた。現在の見える部分の切り出しだけでは、自然な瞬き・開口・顔の向きは完成しない。**

## 実行した工程

1. CPU上のSAM 2.1 tinyで点・枠・除外点を使い、見える髪・顔・衣装・左右の目・口など17候補を抽出。名前からの自動判定ではなく、手動指定した評価。
2. SAMだけの全体切り抜きで、白い衣装や長髪の欠け・穴を確認。背景除去向けのローカルBiRefNet-General-Liteでも全体を抽出して比較した。
3. BiRefNetの透明度を使い、RGBは元画像から取得。rembgが返したRGBAは半透明の縁でRGBが暗く変化していたため、そのRGBをそのまま使わず、元の色を保持した。alpha0の画素はRGBAをすべて0にする。
4. 全体の抽出から、顔→頭の髪→ジャケット候補を除いた左右の髪→未分類の残り、の順に重複しない5枚へ分けた。左右の目と口の見える部分は別のSAM候補を使用。
5. 素材引き継ぎZIP→このアプリのPSD変換→別プロセスのpsd2live→実MOC3/model3/テクスチャを生成。PurismCoreで初期化・各パラメーターの値変更・実テクスチャ描画を確認した。

外部ツールの固定SHA、利用条件、起動方法は [モデル生成試作](MODEL_BUILD_TRIAL.md)を参照。公式Cubism Core、VTube Studio、Windows/スマホ実機の検証ではない。

## 観察結果

| 対象 | 実際に確認できたこと | 残る問題 |
|---|---|---|
| 全体の輪郭 | BiRefNetで白い衣装の大きな欠け、長髪の多数の穴が減った | 毛先の半透明・白い縁は未保証。アプリ画面はまだSAMのまま |
| 5枚の再合成 | 抽出した全体と画素差0、パーツ同士の重複0、未割当0 | 元画像全体の完全抽出や、動かしたときの品質を意味しない |
| モデル生成 | 実MOC3/model3/4枚のテクスチャを生成し、独立ランタイムで読み込み・描画成功 | 公式Core/VTS互換と完成品質は未確認 |
| 左右の目 | `ParamEyeLOpen` / `ParamEyeROpen` は存在 | 値を変えても形状差0、閉眼画像との描画差0。目が閉じない |
| 口 | `ParamMouthOpenY` で形状と描画に変化 | 閉じた口を含む肌の小パッチが変形するだけで、口内部はない |
| 顔の向き | `ParamAngleX` ±10で実画素が変化 | 額の髪際や首などに隙間が出る。現在は自然に使える状態ではない |
| 顔と目・口 | 元の目・口が肌に残り、別パーツにも同じ画素がある | 目を隠したり動かしても元の絵が残る。肌の下地が必要 |

元画像は853×1280。改善した全体抽出のalpha>0は345,564画素。5枚の内訳は肌6,877、頭の髪25,707、左右の髪23,688/23,505、残り265,787画素。残りを便宜上`body`と呼ぶが、分類できていない髪や肌も含み、衣装分離の完成品ではない。前髪/後ろ髪、白目/瞳/まつげが正確に分かれた結果とも扱わない。

元RGBを保持した版のモデルは10描画部品/2,313頂点。全体512px・顔512pxの比較で左右/両目閉は画素差0、口開は全体149画素/顔2,163画素の変化。口の微小変化を開口成功とは扱わない。顔左右では額・髪際・首の破れを目視した。

スマホ幅390pxのChromiumでも、実画像の作業ZIPを読み込み→実サーバー生成→モデルZIPの保存まで操作。重複候補3件/動きが確認できない目2件の画面通知、独立ランタイムの検査結果を確認した。モデルZIPは3,360,125 bytes。画面には制作向け7パーツを表示し、基本構成の残り1枚を含む全8パーツと元画像を作業保存で保持（バイト一致）、画面エラー0。スマホ実機や通常APIの全自動分離を確認したという意味ではない。

SAMの最初の11候補は約4.36秒、追加6候補は約3.59秒。BiRefNetはモデル読込約4.94秒・推論約14.28秒（CPU、alpha mattingなし）。この画像と今回の環境での参考値であり、スマホ上の処理速度や全画像の精度を保証しない。モデルの重みは正規配布をTLSで取得し、rembg埋込MD5 `4fab47adc4ff364be1713e97b7e66334`と一致。取得した重みのSHA256は`5600024376f572a557870a5eb0afb1e5961636bef4e1e22132025467d0f03333`。

## 今回アプリへ反映した改善

- AI分離PNGの完全透明部分に元画像のRGBが残る問題を修正。見える画素と部分的な透明度は保持する。モデル用PSDも古いPNGのalpha0 RGBを落とす。端末にある過去の素材・作業ZIPを自動で書き換える処理はない。
- 顔の下地と目・口の元位置で、一定数以上の同色画素が重なる場合に候補をレポートし、生成後の画面に注意を表示。RGBが加工された画像では検出できないことがあり、別の絵でも同じ色が重なり得るため、候補の有無を合否としない。
- 推奨6パラメーターについて、未検証/IDなし/変化なし/変化ありを記録。名前があるだけで動くとは判定せず、変化なし等を画面に表示する。カスタムIDは手動対応できるので生成を拒否しない。変化があっても自然な表情の証拠にはしない。
- 有効な閉じ目・閉じ口を、通常表示で見えないという理由で生成入力から落とす問題を修正。外部生成器の開閉による透明度切替に渡し、レポートに含めた差分の役割を残す。無効素材は引き続き除外。追加素材を自動で作る処理ではない。
- 実MOC3を黒・白・チェッカー背景で比較描画する`render-preview.py`を保存。顔と全身をそれぞれ同じ倍率・範囲で比較し、適用値、見つからないID、画素変化を記録する。画像はGitの外の新しいフォルダーだけへ出す。
- 生成テクスチャの展開後合計を64MiB以内に制限。今回は2048pxを4枚使用した。これはモデル側の画像量の上限で、スマホが64MiB以内で動作するという保証ではない。

差分の修正は自作素材からの実MOC3でも検証。左右の閉じ目の透明度は通常0/0、左閉1/0、右閉0/1、両閉1/1。閉じ口は通常1→口開0へ切り替わった。15描画部品のモデルで整合性と全サンプルの有限値を確認。入力へ差分を渡す修正の証拠であり、今回の提供画像に閉眼/口内部を生成できたという証拠ではない。

## 次に直す順序と完了条件

1. **背景除去を素材準備へ接続**：今回の良い輪郭を画面で使えるようにする。再試行・中止・作業保存と、元位置/色の保持を確認する。
2. **正面の瞬き・口**：元の目・口を含まない`face_base`、左右の白目/瞳/まつげ、開いた口内部と閉じた口の素材を用意する。元画像にない肌・瞳の続き・口内部は切り抜きだけでは作れない。既存PNGの持込経路を使え、描き足し方法は別途決める。
3. **差分を使って再生成**：今回修正した生成入力の差分対応を使い、用意した閉眼・閉口をモデルへ渡す。無効にした素材は使わない。アプリの独自メッシュ/範囲/親子キーの転写とは別の対応。
4. **実モデルを比較**：片目/両目/口の0・0.5・1を描画し、元の瞳の残り、二重線、透明な穴、頬の引き伸ばしを確認する。正面で合格してから顔の向きと組み合わせる。額・首・髪の欠けが残る間は完成としない。
5. **VTube Studio**：目的の端末で読み込み、追跡と保存後の再読込を確認する。独立ランタイムの検査では代用しない。

通常のコード修正・テストは継続承認内で進める。今回、隠れ部分の画像生成・外部画像送信・アプリ公開・main統合は行っていない。

## ローカルで描画を再確認

生成モデルと信頼できるPurismCore共有ライブラリを別途用意する。Pythonにはnumpy/Pillowが必要（AI用`.venv`でも利用可能）。

```bash
python3 scripts/model-build/render-preview.py \
  --library /path/to/libPurismCore.so \
  --model /path/to/character.model3.json \
  --output /tmp/new-character-preview \
  --height 512
```

必要なら`--face-box .30 .035 .70 .23`のように、全ポーズ共通のモデル範囲に対する左/上/右/下の割合を指定する。未指定の顔範囲はIDによる推定であり、顔検出ではない。最近傍サンプリング・物理なしの診断用描画。未対応の合成方式や入れ子のマスクを黙って近似せず拒否する。マスク用alphaはRGBA配列からコピーし、不要な4成分の保持を避ける。

今回の素材・モデル・比較レポートはこの環境の`/tmp/ai-live2d-character-trial/`にある。一時環境の終了で消える可能性があり、GitHubへの画像保存や端末間の自動同期はない。次回の環境ではコード/記録はブランチから再開できるが、実画像の再評価には画像と外部生成ツールの再準備が必要。
